# Issue 473: bounded retrospective source windows

## Reproduction and persisted retry loop

The regression fixture uses seven typed user messages, each containing a multi-hundred-KB Chromium GPU log paste. Before source guards, the assembled friction-gate request is **2,185,146 bytes / 682,785 estimated tokens**. For the fixture child's 8,000-token usable input, the shared historian refusal margin admits 7,760 tokens, so `producerWindowFailureReason` classifies the request as `producer_source_exceeds_window`. The old failure path threw before returning a schedule patch: `task_schedule_state.retrospective_watermark_ms` therefore did not move (and `last_run_at` also advances only on completion). The next run queried from the same content watermark and rebuilt the same oldest-first source window, making a provider size rejection permanent rather than transient.

With the guard enabled, every typed user message is clamped to 8,000 characters with equal head/tail context and an explicit middle marker before either OpenCode SQLite or Pi JSONL data enters a prompt. The same fixture is admitted as an oldest-first prefix of three messages: **25,086 bytes / 7,754 estimated tokens**, below the 7,760-token limit, with the source frontier recorded at timestamp 120 so later rows remain pending. Prompt admission reuses `producerInputTokenLimit` and its 3% estimator margin; the effective budget is the smallest known usable input window in the configured child model chain (128K conservative fallback when model metadata is unavailable).

A configurable recency bound now lives at `dreamer.tasks.retrospective.recency_days` (default 30). The reader starts at the later of the persisted content watermark or the recency cutoff minus one millisecond. Expired rows are never collected, while the returned frontier advances past them even if there is no recent message. The shared reader owns clamping, admission, and frontier calculation, so the Pi JSONL provider receives exactly the same behavior without a second implementation.

Provider size errors are classified by the existing overflow detector. The first rejection persists a halved input budget while leaving `retrospective_watermark_ms` unchanged because no source has been accepted as processed. A second rejection at that same watermark persists the furthest safely admitted frontier and logs that the repeatedly rejected source window was abandoned. The next run starts after that frontier; the integration test rejects two child requests and proves the third prompt's source labels are disjoint from the first.

## Reporter reply draft

Thanks for the precise DB measurements and the June-to-September example — they exposed both the missing byte/token bound and why the retry was permanent. This ships in **v0.42.7**: retrospective now clamps oversized user pastes head+tail, admits the oldest-first batch against the child model's usable input window with the historian's estimator margin, expires source lines after 30 days by default (configurable with `dreamer.tasks.retrospective.recency_days`), applies the same reader to OpenCode and Pi JSONL, and makes overflow retries shrink once then advance the safely scanned frontier so the same rejected request cannot recur forever.
