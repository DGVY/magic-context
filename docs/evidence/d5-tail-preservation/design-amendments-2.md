# D5 tail preservation — normative amendments §18–§20 (continues design-amendments.md; later sections override earlier text)

## 18. Amendments from the two independent seats (v3.6; seat A = wi_1c9e838b, seat B = wi_7ca5e6e8, both AMEND on v3.5; reports under .cortexkit/alfonso/reviews/d5-uncovered-tail-2026-09-11/design-gate-seat-{A,B}.md). Converging findings are merged; each carries the constructed sequence in the seat report.

18.1 **Resolve reports the current P fence, not one attempt's fate (B1, A1 first half).** `attempt.resolve` returns `{attempt_outcome, p_fence: {state: none|SEALED{receipt_id}|REDEEMED{successor_key}, fence_generation}}` in one transaction; the gateway admits an ordinary P request only on `p_fence.state == none`, never on `attempt_outcome == REFUSED` alone (a REFUSED/tombstoned attempt proves that attempt cannot seal, not that P is unfenced — another attempt may hold the fence). Coalesced attempts: the seal transaction records every concurrent attempt_id that observed the SEALED row as a durable alias on the receipt, so resolve(any alias) returns SEALED. Normal P admission CAS-checks `fence_generation` independently of any attempt state. Gateway side: the durable attempt identity + ingress ownership record is written BEFORE dispatching `prepare` (not merely before the first reply byte — A1: a crash between prepare and the attempt record otherwise classifies a SEALED P as unfenced); after restart the gateway queries P's active receipt before admitting any ordinary request.

18.2 **Release is a terminal send-revocation protocol (A1 second half, B2).** Gateway: an atomic durable transition `RELEASE_INTENT → NEVER_SEND` that serializes with every reply permission and forbids registering new retries or flipping any bit afterwards; a retry worker holding a cached SEALED response must re-check `NEVER_SEND` under the same lock before emitting the placeholder. MC: `release` is a CAS `SEALED → RELEASED` (idempotent, refuses on any other state) that serializes with `redeem` (both CAS the same receipt row; exactly one wins). **Transfer on release:** the release transaction merges every receipt-held command (`pending` frozen into A at seal and `post_seal_drops`) back onto P's queue with provenance and dedup by (command_id, target), preserving ledger rows, and clears the admission fence in the SAME transaction — no parked drop is ever stranded on a swept receipt. Pins: C-before-release, C-after-release, concurrent release/routing, release-vs-reply, release-vs-redeem, crash-before-gateway-attempt-record.

18.3 **Two anchor identities, and publication across the retained boundary row (A3, B3).** The core and wire distinguish `coverage_identity` (the last real compartment's end: `mid1798#idx`, used by m0/m1 composition, historian eligibility, ctx_expand range, coverage derivation) from `continuation_identity` (the native anchor `mid1940`, used by ordinal rebasing, the host compaction marker, reconcile/trim, and the live-boundary availability guards at transform.rs:4812–4821/4912–4917/7866–7904). Rule: the live-boundary guards validate the `continuation_identity` against the native request (present by construction) and the `coverage_identity` against the RECEIPT (a receipt-backed presence proof: the block is in the carried manifest or in a real compartment) — never a global bypass of mint/revert guards, and never a numeric substitution. Historian publication on S may cross the retained `[1940,1940]` anchor row: the store's overlap check (mc-store lib.rs:16663–16690) exempts rows with `episode_type='lineage_boundary'` from overlap (they are non-covering anchors kept in a separate role), a crossing fold either absorbs the anchor row (anchor metadata preserved on the new compartment) or the anchor is moved to the fold's end — one rule, pinned by: partial inherited fold (1799–1905), fold crossing the anchor (1799–1950), repeated/nested folds, and assembly-snapshot/generation ordering vs publication sequence.

18.4 **Optional folded frontier and the zero-compartment case (A5).** `folded_frontier` is `Option<ordinal>`; with no real compartment on S, the historian's eligible head is `first_inherited_ordinal` (the carry's first manifest ordinal), not `folded_frontier + 1`; lib.rs:5198–5226's `continued_ordinal_offset_missing` arm must not fire when a carry exists; ordinal 0 is a real CC ordinal (lib.rs:11902–11905) — no unsigned arithmetic assumes ≥1. Pins: no-fold-yet with carry; a real fold ending at ordinal 0; the specimen 1798/1940 shape.

18.5 **Negative-state retention and generation-fenced deletion (A4, B4).** Tombstones are never reclaimed while the attempt could still seal: every prepare/resolve/seal carries the session's `incarnation` (a monotonic generation bumped on session.delete/recreate); a delayed prepare with a stale incarnation refuses at the seal CAS regardless of tombstone presence, which makes tombstone rows reclaimable after the incarnation advances. Admission quota: a per-session cap on outstanding non-terminal attempts (refuse `attempt_quota` before allocation) and a bound on retained negative rows per session (oldest-first retirement only when their incarnation is stale). Deletion scope: receipts/archives are session-scoped rows keyed by `owner_key`; `deleteSessionScopedRows` (mc-store lib.rs:7444–7485) deletes by `session_id` today — the D5 tables are deleted by `owner_key`, which the redeem transaction transfers to S, so deleting P after redeem cannot remove S's protecting reference; blobs are refcounted by `archive_id` across receipts in every state including tombstone-free negative rows; nested descents transfer ownership hop by hop; a stale request after delete/recreate is refused by incarnation. Forced deletion is the one intentional destructive exception and is logged as such.

18.6 **Count the output carve exactly once (B5).** `usable_soft` is already `window − output_reserve` (window-geometry.ts:514–620; Rust geometry is host-resolved). The budget test is `estimate(system + tools + m0 + m1 + carry + anchor_reserve) ≤ usable_soft` — output_reserve is NOT added again. If an additional safety margin is wanted it is a named separate constant, not the scheduler's reserve. Pins: shared-upfront, shared-truncating and separate geometries, explicit output overrides; the 200k/20k configured case (170k projected fits, must not refuse).

## 19. Budget accounting made explicit; admission semantics (v3.7, Thalamus pm_548e4661)

19.1 **Reserve accounting, stated per source.** The CC gateway's wire geometry (thalamus proxy.rs:185–205) is NOT net of an output reserve: for context-1m models `usable_hard == usable_soft` with no subtraction; for others `usable_soft` is a configured scheduling value (default 167k) and `usable_hard` = 200k, overrides may exceed hard; TransformInput carries no output_reserve. MC's OpenCode/Pi geometry (window-geometry.ts:514–620) DOES carve `output_reserve` into `usable_soft`. So "the reserve was removed once" is true on the TS legs and "zero times" on the CC wire. The budget therefore uses two named variables and states the conversion: `fit_soft = usable_soft_wire` when the wire declares its geometry already net of reserve (a `derivation` flag the geometry struct carries — MC legs set it; CC does not) and `fit_soft = usable_soft_wire − output_reserve_mc` otherwise, where `output_reserve_mc` is MC's model-resolved reserve; **and independently** the hard test `estimate(...) + output_reserve_mc ≤ usable_hard_wire` — soft alone never certifies fit. Overrides above hard are clamped to hard for the fit test. Both variables, the flag and the clamp are recorded in the receipt's budget block. Pins: CC 167k/200k geometry with a carry that fits soft but not hard (refuse), the 1m case (hard == soft), the TS-leg case (reserve counted once), an override above hard (clamped).

19.2 **fence_generation is consumed at admission, not cached.** The gateway either holds exclusive ingress ownership for the (session, agent) across resolve → admit, or re-checks `fence_generation` in the actual admission step; a value read earlier is never treated as standing permission. Pin: resolve returns none, a concurrent prepare seals, the admission re-check refuses.

19.3 **Release safety recorded as target semantics.** 18.2's gateway clauses are safety semantics to implement, not a claim about today's gateway; NEVER_SEND spans all aliases/retries for a receipt; if MAY_HAVE_REPLIED is already true, release is never claimed safe; revocation precedes the remote release call; cached SEALED responses re-check permission immediately before acquiring the send right; MC restores frozen + post-seal commands to P atomically on release.

19.4 Remaining before spec: Thalamus's consumer map into 16.3/18.3; the estimator/retained-envelope lifecycle (how long the gateway retains the normal-turn envelope, what invalidates it, what MC does when it is absent — currently `budget_unknown` → refuse) as an explicit section; then the Athena refire on the final text. Status: AMEND folded, not SHIP-DESIGN.

## 20. Retained-envelope lifecycle (v3.8; closes 19.4)

The budget-evidence contract (§17.1) needs the most recent NORMAL-turn outbound envelope on P as the source of the system and tools byte segments. Lifecycle:
- **Retention (gateway):** the gateway retains, per (session, agent), exactly ONE envelope record: `{envelope_id, request_sha256, captured_at, model, system_bytes, tools_bytes, geometry, reserve_accounting}` from the most recent forwarded normal turn (not a compaction/summary request, not a refused/503 turn, not a retry). Overwritten on each newer normal turn; never partially updated (write-then-swap).
- **Invalidation:** a model change, a tools-set change (sha of the tools segment differs), or a system change (sha differs) makes the record simply the newer one — there is no "stale" state; the record is always the latest observed. It is absent only before the first normal turn of the session or after a gateway restart that did not persist it (persistence is required for the record to survive restart; if the gateway cannot persist envelopes, absence after restart is the honest outcome).
- **Use at prepare:** the gateway passes the record by value; MC records `envelope_id` + `request_sha256` in the receipt's budget block and runs its estimator over the byte segments. MC never caches the envelope beyond the receipt.
- **Absence:** no record → `budget_unknown` → REFUSE (503 to the compaction request; the harness's own compaction proceeds; no seal, no fence). This is the deliberate liveness cost of unknown ≠ zero; it is expected only on the first turn of a fresh session or immediately after a non-persisting gateway restart, both stated in the refusal reason.
- **Mismatch:** if the envelope's model differs from the compaction request's model, MC refuses `budget_model_mismatch` (the summary turn's model is not the successor's serving model; the estimator has no basis).
- **Pins:** first-turn compaction refuses budget_unknown; a compaction after a normal turn seals with the envelope id recorded; a tools-set change between the normal turn and the compaction uses the NEWER record (no stale refusal); a gateway restart without persistence refuses with the stated reason; model mismatch refuses.

§20 gateway constraints (v3.9, Thalamus pm_9c63ecbb — normative, carried into the final gate):
1. **Retry-inclusive selection.** A successfully forwarded normal turn that was itself a harness retry IS the latest valid normal envelope; exclusion applies to rejected/unmanaged/summary attempts, not to retried requests (otherwise a 503 recovery with new tools/model leaves an older record indefinitely).
2. **Causal-order swap.** The record is replaced only when the incoming envelope's `(gateway boot id, ingress sequence)` is strictly greater than the stored record's, and the session/agent/lineage/incarnation match; an older overlapping request that completes last is discarded, not written. The update point is the moment the forwarded request is committed to send (not on completion). A "newer-unusable" tombstone: when a newer normal turn was forwarded but its envelope could not be persisted, the record is marked `newer_unusable{sequence}` so an older record is never presented as current — absence with a reason, not a stale record.
3. **Persistence required.** Restart survival is promised only when the gateway persists the record durably BEFORE the provider send (write-ahead: persist → send; a crash between the two leaves a record that describes a request that may not have been sent, which is still a valid envelope description); a non-persisting cache is a degraded mode that must be declared and yields `budget_unknown` after restart — it is not the design. Disk write failure → mark the slot unusable (tombstone as in 2). A restored older gateway DB is detected by the incarnation/boot-id in the record disagreeing with the live session incarnation → absent, never "fresh by presence".
4. **Envelope is evidence of THAT request only.** The record carries header-derived geometry, profile, guidance-surface and tool-surface identities (hashes) alongside the raw segments; at prepare MC validates envelope identity against the compaction request's declared identities (model equality alone is insufficient) and the receipt records age (sequence distance) and any identity mismatch as `budget_evidence: {fresh | aged{n} | mismatch{field}}` — mismatch on tools/system/profile refuses `budget_evidence_mismatch`; the final outgoing-request geometry check on the successor's first pass remains mandatory regardless (the estimate is admission evidence, not a guarantee); summary-request `max_tokens`/tools are never substitutes.
5. **REFUSE semantics restated.** "503, harness compaction proceeds" means the COMPACTION FAILED at the gateway: the tested AUTO path resumes its ordinary request with old history (no provider-summary fallback is performed by anyone); no destructive placeholder and no fence exist only on an authoritative REFUSED; UNKNOWN still resolves through the attempt machinery (§15/§18.1).
These are implementable constraints; no current gateway persistence API is claimed to exist.

§20 cautions (Thalamus pm_301224c3, final-gate inputs): (a) a restored/rolled-back gateway DB cannot be detected from ids stored only inside that DB; the restore fence needs an INDEPENDENT witness — the session incarnation held by MC (store.db) is that witness: at prepare, MC compares the envelope's recorded incarnation against its own; an envelope older than MC's incarnation for the session is absent-by-rollback. Ordinary restart changes boot id by design and must NOT invalidate an otherwise durable envelope — boot id is used only for causal ordering within a boot, incarnation for validity across restarts; restart survival is claimed for that bounded guarantee only. (b) Summary requests may legitimately differ from or omit fields of the normal envelope; identity validation is against the intended NORMAL projection identities the successor will serve under (model, tool-surface identity as MC resolves it for the session, guidance surface), never blind equality to the raw summary shape. Consumer map: seat A (§Q4) and seat B (§4) each produced a verified consumer inventory; §16.3/§18.3's table is built from their union with explicit gaps marked, and Thalamus's supplementary map (bg_4510ddad) is merged when delivered — it is not a blocker for the final gate.

§20 witness scope (Thalamus pm_44b35e6c, for the refire): the incarnation witness is BOUNDED — an envelope with an OLDER incarnation than MC's is rejected; an EQUAL incarnation does not detect a rollback to an older envelope from within the same incarnation, and a joint restore of MC's store rolls the witness back too. Those two cases are explicit limitations, not covered: freshness there depends on the recorded normal-projection evidence agreeing with the compaction request's declared identities (18.4-style validation), and where that cannot decide, the outcome is UNKNOWN/REFUSE, never a claim of universal rollback detection.
